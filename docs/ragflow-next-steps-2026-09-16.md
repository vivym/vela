# RAGFlow 下一步：先完成 PDF 质量验收，再闭环问答

当前已经验证了双 GPU vLLM Embedding/Reranker、RAGFlow 索引和检索，以及一个
包含原生文字、表格、双栏、扫描页的 PDF。当前主要缺口是 **解析质量**：表格漏掉
`Cedar-C` 的节点数 `4`，双栏步骤交错。Chat 模型仍未配置。

依据：[模型部署证据](qwen3-model-worker-evidence-2026-09-16.md)、
[PDF 验收结果](ragflow-pdf-validation-2026-09-16.md)。以下是待执行计划，不是已完成结果。

## 第一优先级：修复两个已复现的 PDF 质量问题

下一轮工作只以这两个确定缺陷为目标：

1. 用已固定 PDF 检查 DeepDOC 中间结果，定位表格数字从哪一步丢失：原生字符提取、
   OCR 文字框、表格单元格关联或最终序列化。独立 `pdfplumber` 已能读出该数值，
   因此可作为对照，但不能据此推断它能取代扫描页 OCR。
2. 跟踪双栏的检测、排序和合并，定位 `B1 A1 A2 B2 A3 B3 B4 A4` 的形成位置。
   不能通过修改标准答案或手工补全索引内容来“通过”测试。
3. 优先核实上游是否已有针对性修复；若修复需要维护大范围私有分支，在隔离测试库
   用同一组输入对比替代解析器，再选择质量、耗时、资源成本合适的一条路径。
   解析器兼容性和模型依赖需要实际确认，当前没有足够证据直接决定更换。
4. 按文档类型检查分块和定位，避免多个章节跨页混在一个片段里；需要保留表格表头、
   栏内顺序和可回溯的页码。分块调整不应破坏已有 Markdown 和扫描页检索。

固定样本的完成标准：15/15 内容检查、3/3 表格行完整、双栏顺序正确、6/6 问题的
检索结果含所需答案证据；OCR 五个专用字段继续通过。随后用独立的普通文字、
数字密集表格、双栏/扫描材料做回归，避免只修到合成样本能过。

这一阶段的结果应是一套通过上述验收的解析配置/镜像和复测记录；若候选方案仍有
缺陷，明确指出未通过项，不能用 `DONE`、命中率或高重排分数替代内容完整性。

## 第二优先级：配置 Chat 模型，完成可核对引用的问答

解析质量过关后，选择并部署适合当前 GPU 与并发目标的 Chat 模型，配置 RAGFlow
聊天助手。Chat 模型需要单独核算显存与 GPU 预算；现有两张卡已由 Embedding 和
Reranker 的 Pod 分配，不能按显存剩余量推断 Kubernetes 还能直接调度第三个模型。

复用固定 PDF 和独立样本，验证“上传 → 解析 → 向量化 → 检索 → 重排 → 回答 → 引用”。
同时加入无答案问题：证据中缺失的数值应明确说明无法确认，不能编造。
当前尚无 Chat 模型，因此之前的“5/6 有答案证据”不等于生成式回答正确率。

## 第三优先级：解析性能、指标和使用体验

本次 4 页 PDF 任务耗时 101.85 秒，CPU OCR/版面/表格占主要时间，而 GPU Embedding
仅 0.17 秒。该结果包含初始化，只能定位本次瓶颈，不能推算稳定吞吐。

质量稳定后，测量冷启动/热运行以及单任务/多任务表现，再决定 DeepDOC GPU 化、
解析器替换或 Executor 并发调整。GPU 化不会自动修复丢失数值和错序。

补齐解析队列、各阶段耗时、失败率、内存/GPU 占用，以及 Reranker 请求/排队指标；
在 Grafana 中查看并配置告警。团队试用前复核企业 DNS、私有 CA 信任、文件权限隔离
和备份恢复。当前单副本本地缓存/存储的故障迁移能力仍是独立的后续事项。
